## 文件交接规则

- **文件上传区/**：新资料入口，处理后文件会被移走（move，不是 copy），不保留副本
- **文件下载区/**：对外交付物备份，可随时删除、移动、复制，不影响主工作区
- 用户确认要交付的成果时，主动询问是否需要复制到下载区

## 工作记录规则

- 每天自动创建当日工作记录文件（格式：`YYYY-MM-DD.md`）
- 只记录用户明确确认的阶段性成果，不记录讨论过程或未验证的想法
- 记录格式：时间 + 操作/成果 + 状态/备份位置
- 跨窗口对话时，先读取最近 3 天的工作记录了解上下文

## 规则优先级

- 用户当前明确指令 > 本文件（AGENTS.md） > SOURCE_OF_TRUTH.md
- 规则之间发生冲突时，询问用户澄清，不静默选择其中一条

## 工作区自我进化（主动触发）

本工作区具备自我学习和进化能力，通过分析用户的真实工作记录，发现可以自动化的重复模式。

### 触发条件

Agent 每次读取 `SOURCE_OF_TRUTH.md` 时，自动检测：
1. 检查 `工作记录/` 目录的文件总数
2. 对比 `SOURCE_OF_TRUTH.md` 底部元数据中的"下次分析阈值"
3. 达到阈值 → 主动触发自我进化分析

**阈值设计**：
- 首次触发：30 条工作记录
- 后续触发：每增加 30 条（60, 90, 120...）
- 最小间隔：与上次分析相比至少新增 20 条

### 数据来源：工作记录 = 最强真源

不看文件结构、不看文件名，**看用户实际做了什么**。

工作记录保留了用户的真实业务事件：
- 完成的任务
- 创建的文件
- 重复的问答
- 固定的流程

这是比文件目录更可靠的数据源。

### 分析流程

#### 第1步：快速扫描，建立索引
- 读取所有工作记录的文件名、日期、标题
- 提取每条记录的摘要（不全文读取）
- 建立时间线索引

#### 第2步：关键词聚类，识别任务类型
- 按关键词对记录进行分组
- 例："新项目"、"接入"、"需求" → "新项目启动"类
- 例："复盘"、"统计"、"数据" → "数据复盘"类
- 统计每类出现的次数

#### 第3步：抽样验证，确认固定模式
- 筛选重复 **3 次以上** 的任务类型
- 每类抽取 2-3 条代表性记录，读取完整内容
- 验证是否存在稳定的操作流程
- **总共只读 10-15 条完整记录**，不是全部

#### 第4步：生成建议表格
创建文件：`工作区优化建议/YYYY-MM-自我进化建议.md`

内容包含三列表格：

| 候选 Skill | 工作记录中反复出现的操作 | 应固定的流程与完成标准 |
|-----------|------------------------|---------------------|
| 建议的 skill 名称 | 列出实际的工作记录标题作为证据 | 说明这个 skill 会做什么、不会做什么 |

**表格要求**：
- **候选 Skill**：清晰的名称，例如"新项目启动"、"周期复盘"
- **证据来源**：列出实际的工作记录标题，证明这是真实重复的工作
- **流程标准**：明确说明 Agent 承担什么、用户确认什么、不自动做什么

#### 第5步：主动告知（惊喜时刻）
在 Agent 当前回复中，自然插入：

```
💡 工作区进化提醒

我注意到你的工作记录已经累计了 XX 条，分析了你过去的工作模式。

值得整理成一组自己的工作 Skill。我建议先定下 N 类，其中 M 类优先制作。
这一轮没有创建或改文件。

我已查看代表性的 XX 条记录，覆盖 N 个不同的任务类型。
不是把所有记录全文读完了；下面是有实际重复记录支撑的第一版归纳。

[三列表格]

这些建议靠谱吗？如果觉得方向对，我可以生成详细的 skill 草稿。
你也可以告诉我哪些要调整、哪些不需要。
```

### 输出原则

#### 1. 先沟通，后落盘
- **只建议，不自动创建**
- 生成表格让用户审阅
- 用户明确说"生成"、"做吧"、"可以"后，才创建 skill 文件

#### 2. 说清楚边界
每个建议的 skill 都要明确：
- ✅ Agent 会做什么（自动化的部分）
- ⚠️ 用户需要确认什么（人工决策的部分）
- ❌ 不会做什么（避免误操作）

例如：
- "保留人工确认需求，不自动发出去"
- "Agent 承担统计，不编造未记录的数据"
- "只建结构，不预填内容"

#### 3. 不编造，只归纳
- 建议必须有实际工作记录支撑
- 表格中列出具体的记录标题作为证据
- 找不到 3 次以上重复的模式，不建议

#### 4. 说明抽样方法
明确告知用户：
- "我已查看代表性的 13 条记录"
- "不是把所有记录全文读完了"
- "下面是有实际重复记录支撑的第一版归纳"

### 避免重复打扰

分析完成后，更新 `SOURCE_OF_TRUTH.md` 底部的元数据：

```markdown
## 工作区元数据（Agent 自动维护）

- 工作记录总数：35 条
- 最后自我进化分析：2026-09-23（基于 35 条）
- 下次分析阈值：60 条
- 累计生成 skill：2 个（py-new-client, py-monthly-review）
- 用户拒绝的建议：[] （不再重复提）
```

记录：
- 最后分析时间
- 基准条数
- 已生成的 skill
- 用户明确拒绝的建议（下次不再提）

### 可能识别的模式类型

根据工作记录，可能发现的自动化机会：

#### 1. 文件操作模式
- 每次新项目都创建"需求、合同、记录"三个文件
- 每次新课程都创建"大纲、逐字稿、反馈"目录结构

#### 2. 固定问答流程
- 接项目时总是问"预算、时间、范围"
- 交付前总是确认"版本、格式、截止日期"

#### 3. 周期性任务
- 每月都做"产出统计 + 进度 + 变化分析"
- 每周都做"社群内容规划 + 互动跟踪"

#### 4. 内容生产流程
- 课程都经历"大纲 → 逐字稿 → 反馈整理 → 迭代"
- 文章都经历"选题 → 大纲 → 初稿 → 修改 → 发布"

#### 5. 数据同步任务
- 工作进展更新后同步到飞书任务/日程
- 对外交付后更新项目状态和发票记录

### 生成 Skill 草稿的标准

用户确认方向后，生成的 skill 草稿应包含：

#### SKILL.md 结构
```yaml
---
name: skill-name
description: 一句话说明这个 skill 做什么
when_to_use: 用户什么时候需要调用
---

# Skill 名称

## 功能说明
[清晰描述这个 skill 的作用]

## 使用方法
/skill-name <参数>

## 固定流程
1. 第一步（Agent 自动执行）
2. 第二步（用户确认）
3. 第三步（Agent 完成）

## 边界说明
- ✅ 会做：...
- ⚠️ 需要确认：...
- ❌ 不会做：...

## 示例
[实际使用示例]
```

#### 草稿保存位置
`工作区优化建议/skill-drafts/<skill-name>/SKILL.md`
